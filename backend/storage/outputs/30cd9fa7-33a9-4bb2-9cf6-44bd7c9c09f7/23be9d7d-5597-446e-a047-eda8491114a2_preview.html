● 一、先把需求翻译成技术改造目标

● 你这个需求，建议 Claude Code 按下面的理解来做：

1）访问模式改造

现状大概率是：

- 普通用户、管理员都走统一登录

- 登录后再按角色控制页面和接口权限

改造后变成：

- 普通用户入口：打开浏览器地址即可直接进入普通用户业务页面，无需输入账号密码

- 管理员入口：提供独立访问地址，管理员仍然需要登录

- 管理员现有能力完全保留

2）身份模型变化

普通用户不再是真正意义上的“登录用户”，而更像：

- 一个匿名但受限的内部访问身份

- 或者一个系统自动赋予的内置 guest / internal_user 身份

也就是说，普通用户访问时，系统前后端都要把他当成一个固定权限的“免登录用户角色”处理。

3）审计与历史变化

普通用户：

- 不再保留个人审计历史

- 不再要求按个人账号追踪操作记录

管理员：

- 审计、历史、权限体系保持不变

4）核心边界

不能因为做了免登录，就把系统变成“谁都能管后台”。

所以必须明确：

- 普通用户只能访问普通用户页面和普通用户接口

- 管理员页面、管理员接口必须继续受保护

- 前端路由、后端接口、中间件、菜单、历史记录逻辑都要分开处理

● 二、你要提醒 Claude Code 重点关注的风险点

● 这部分很关键，不写的话，Claude Code 容易只改前端按钮，没改后端安全。

● 重点风险 1：不能只去掉前端登录页

● 如果只是前端直接跳转，而后端接口还是默认靠登录态区分，就会出问题。

● 必须检查：

- 后端认证中间件

- 角色判断逻辑

- 路由守卫

- 接口鉴权装饰器 / dependency

- 审计日志写入逻辑

- 用户历史记录关联逻辑

重点风险 2：普通用户免登录，不等于管理员也免登录

必须明确做成：

- / 或 /app → 普通用户直接进入

- /admin → 管理员登录入口

重点风险 3：普通用户历史记录逻辑要处理干净

既然“普通用户不再保留审计历史”，那就要让 Claude Code 明确识别以下哪些需要改：

- 审核记录是否还要保存“业务结果”

- 只是“不保留用户维度历史”，还是“连业务处理结果都不存”

- 如果系统很多页面依赖“我的历史记录”，普通用户入口要隐藏或改为空

- 数据库中原来 user_id 非空约束怎么办

你现在这句话更像是：

- 普通用户不保留个人审计历史

- 不一定代表“合同评审结果完全不落库”

所以最好让 Claude Code 先按“保留业务必要数据，但不保留普通用户个人操作历史” 作为默认理解去设计，避免把业务记录全删了。
